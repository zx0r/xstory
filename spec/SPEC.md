# Спецификация системы xstory (System Specification)

Настоящий документ представляет собой формальную, технологически независимую спецификацию системы истории команд терминала. Спецификация описывает архитектурные инварианты, форматы данных, пайплайны обработки, конечный автомат и системные контракты, полностью абстрагируясь от конкретных реализаций, внутренних модулей и структуры исходных файлов.

---

## 1. Модель данных и форматы (Data Models & Storage Specifications)

### 1.1. Персистентный журнал хранения на диске (`history.tsv`)

Хранилище представляет собой append-only лог-файл формата TSV (Tab-Separated Values).

- **Режим доступа:** `O_APPEND | O_CREAT | O_WRONLY` (запись), read-only mmap (чтение).
- **Права доступа файловой системы (POSIX Invariant):**
  - Директория хранилища: строго `0700` (`rwx------`).
  - Файл лога: строго `0600` (`rw-------`).
    Любая автоматическая инициализация обязана принудительно выставлять указанные маски прав.
- **Структура физической строки:**
  Каждая запись занимает ровно одну физическую строку, завершающуюся байтом `\n` (`0x0A`):
  ```text
  <timestamp_ms>\t<duration_ms>\t<exit_code>\t<cwd>\t<command>\n
  ```

#### Спецификация полей

| Индекс | Поле           | Тип данных                | Ограничения и инварианты                                                                               |
| ------ | -------------- | ------------------------- | ------------------------------------------------------------------------------------------------------ |
| `0`    | `timestamp_ms` | `i64` (ASCII decimal)     | Unix epoch в миллисекундах (UTC). Неотрицательное целое число.                                         |
| `1`    | `duration_ms`  | `u64` (ASCII decimal)     | Длительность выполнения в миллисекундах. Значение `0`, если замер недоступен.                          |
| `2`    | `exit_code`    | `i32` (ASCII decimal)     | Код завершения процесса (`0` — успех, ненулевое — ошибка).                                             |
| `3`    | `cwd`          | `String` (UTF-8, escaped) | Рабочая директория в момент запуска. Не может содержать сырых символов `\t`, `\n`, `\r`.               |
| `4`    | `command`      | `String` (UTF-8, escaped) | Полная строка команды (включая флаги и аргументы). Не может содержать сырых символов `\t`, `\n`, `\r`. |

#### Инварианты экранирования строковых полей (`cwd`, `command`)

Внутри полей `cwd` и `command` управляющие символы преобразуются в двухбайтовые последовательности:

- Байт `\` (`0x5C`) $\to$ `\\` (`0x5C 0x5C`)
- Байт `\n` (`0x0A`) $\to$ `\n` (`0x5C 0x6E`)
- Байт `\r` (`0x0D`) $\to$ `\r` (`0x5C 0x72`)
- Байт `\t` (`0x09`) $\to$ `\t` (`0x5C 0x74`)

Все остальные байты передаются as-is. Многострочные команды и команды, содержащие табуляции, схлопываются в единую непрерывную физическую TSV-строку, сохраняя исходную структуру при десериализации.

#### Правила валидации при чтении

- Строка считается валидной тогда и только тогда, когда содержит ровно 4 символа табуляции `\t` (делит запись на 5 непустых по смыслу колонок).
- Если парсинг первых трех числовых колонок завершается ошибкой, либо строка содержит невалидный UTF-8, запись признается поврежденной (corrupted) и молча отбрасывается без прерывания чтения остальных строк.

### 1.2. Модель хранения в оперативной памяти (Columnar In-Memory Arena)

Для обеспечения задержки выборки менее 5 мс на объемах 500 000+ записей система использует декомпозированную колоночную модель (DSM — Decomposed Storage Model) с прямым отображением файла в память (`mmap`) и cache-aligned дескрипторами строк.

#### Структура колоночной арены

В памяти хранятся параллельные непрерывные векторы:

1. `timestamps`: массив `i64` (8 байт на элемент).
2. `durations`: массив `u32` (4 байта на элемент, насыщение при переполнении).
3. `exit_codes`: массив `i32` (4 байта на элемент).
4. `commands`: массив дескрипторов `ByteView` (16 байт на элемент).
5. `cwds`: массив дескрипторов `ByteView` (16 байт на элемент).
6. `masks`: массив 64-битных битовых масок символов `u64` (8 байт на элемент).

#### Формат дескриптора строки (`ByteView`)

Размер: ровно 16 байт, выравнивание `align(16)`. Ровно 4 дескриптора гарантированно упаковываются в одну 64-байтную строку кэша L1 процессора без пересечения границ кэш-линий.

```
+---------------+-------------------+-----------------------------------+
|  len (4B)     |   prefix (4B)     |             data (8B)             |
+---------------+-------------------+-----------------------------------+
| u32 (длина)   | [u8; 4]           | inlined: [u8; 8]                  |
|               | (первые 4 байта)  | out-of-line: buffer_id:u32, off:u32|
+---------------+-------------------+-----------------------------------+
```

- **Режим Inlined (`len <= 12`):**
  - Байты 0..4: полная длина строки в байтах (`u32`).
  - Байты 4..8: первые 4 байта строки (префикс).
  - Байты 8..16: оставшиеся байты строки (до 8 байт).
  - _Следствие:_ строки длиной до 12 байт хранятся полностью внутри дескриптора. Чтение не требует разыменования указателей и обращения к основной памяти.
- **Режим Out-of-line (`len > 12`):**
  - Байты 0..4: полная длина строки (`u32`).
  - Байты 4..8: первые 4 байта строки (для быстрого префиксного сравнения в регистрах CPU).
  - Байты 8..12: идентификатор буфера (`buffer_id: u32`: `0` — первичный mmap-срез, `1` — вспомогательный буфер разэкранированных строк).
  - Байты 12..16: смещение в байтах внутри соответствующего буфера (`offset: u32`).

#### Символьная битовая маска (`mask: u64`)

Для каждой команды вычисляется 64-битный хеш наличия ASCII-символов:

- Диапазон символов `'a'..='z'` и `'0'..='9'` детерминированно проецируется на биты 0..61.
- Бит 63: признак наличия не-ASCII байтов (`HAS_NON_ASCII`).
- **Инвариант быстрого отсечения (Early Pruning):**
  Для маски поискового запроса $M_q$ и маски записи $M_e$:
  $$\text{Если } (M_q \ \& \ \sim M_e) \neq 0 \implies \text{запись гарантированно не содержит всех символов запроса.}$$
  В этом случае выполнение алгоритма нечеткого поиска пропускается без чтения текста команды. Отсекает до 98% записей на уровне регистров CPU.

### 1.3. Форматы передачи данных и протоколы взаимодействия (IPC & Interfaces)

#### Протокол взаимодействия с родительской оболочкой (Shell Integration Contract)

Приложение взаимодействует с вызывающей командной оболочкой через стандартные потоки и коды возврата процесса:

- **`stdout`:** зарезервирован исключительно под передачу результата работы.
  - При успешном выборе команды в TUI выбранная строка пишется в `stdout` без завершающего перевода строки (либо со стандартным переводом строки, считываемым хуком).
- **`stderr`:** полностью зарезервирован под отрисовку TUI, вывод ANSI-последовательностей и диагностических сообщений. Отрисовка TUI поверх `stdout` категорически запрещена.
- **Коды возврата процесса:**
  - `0`: Команда выбрана для немедленного исполнения (Enter). Shell-хук помещает строку в буфер и автоматически эмулирует нажатие Enter.
  - `2`: Команда выбрана для редактирования (Tab). Shell-хук вставляет строку в текущий CLI-буфер ввода без отправки на выполнение.
  - `130`: Пользовательский отказ / прерывание (Esc, Ctrl-C, Ctrl-D). Shell-хук сбрасывает ввод, оставляя приглашение командной строки нетронутым.
  - `1`: Фатальная системная ошибка.

#### Терминальный опрос темы (Terminal OSC 11 Probe Protocol)

Для динамического определения цветовой схемы терминала отправляется объединенный зонд в `stdout`:

```text
\x1b]11;?\x1b\\\x1b[c
```

- Состоит из запроса цвета фона OSC 11 (`\x1b]11;?\x1b\`) и терминального сторожа Primary Device Attributes DA1 (`\x1b[c`).
- **Формат ответа терминала:**
  `\x1b]11;rgb:RRRR/GGGG/BBBB\x1b\` или с терминатором BEL `\x07`.
  Каналы $R, G, B$ нормализуются до диапазона `0..255`.
- **Формула воспринимаемой яркости (ITU-R BT.709 sRGB):**
  $$Y = \frac{2126 \cdot R + 7152 \cdot G + 722 \cdot B}{10000}$$
  Если $Y \ge 128 \implies \text{Светлая тема (Light Mode)}$, иначе $\text{Темная тема (Dark Mode)}$.

### 2.1. Пайплайн записи (Ingestion Pipeline: `record`)

Критический путь фиксации факта выполнения команды. Должен отрабатывать прозрачно для пользователя перед выводом каждого промпта оболочки.

1. **Входные данные:** аргументы командной строки (`command` как массив строк, `exit_code: i32`, `duration_ms: u64`, `cwd: Option<String>`).
2. **Фильтрация нулевой стоимости (Zero-Allocation Pruning):**
   - Конкатенация аргументов команды через пробел.
   - Если строка пустая, содержит только пробельные символы, либо начинается с пробела/табуляции (`ignorespace invariant`) $\implies$ немедленный возврат с кодом `0`.
   - Проверка по точному списку исключений (например, `exit`, `logout`).
3. **Оценка политики безопасности (Security Governance):**
   - Применение регулярных выражений:
     - `Deny`: отказ от записи (токен/команда содержит критические ключи, `AWS_SECRET_ACCESS_KEY`, токены доступа).
     - `Mask`: замена чувствительных значений аргументов на плейсхолдеры.
     - `Allow`: сохранение оригинального текста.
4. **Разрешение рабочего каталога:** если `cwd` не передан аргументом, извлекается системный текущий каталог (`$PWD` или системный вызов `getcwd`).
5. **Сериализация:**
   - Сборка строки записи в переиспользуемый локальный буфер байт `Vec<u8>` с емкостью `64 + cwd.len() + cmd.len()`.
   - Форматирование чисел через буфер без промежуточных строковых аллокаций.
   - Экранирование спецсимволов непосредственно в поток байт.
6. **Атомарная запись:**
   - Открытие файла с флагами `O_WRONLY | O_APPEND | O_CREAT`, права `0600`.
   - Вызов системного `write_all()`. Благодаря флагу ядра `O_APPEND`, позиционирование в конец файла и запись выполняются ядром атомарно на уровне VFS для размеров записей, не превышающих `PIPE_BUF` (обычно 4096 байт). Файловые блокировки не используются.
7. **Бюджет ресурсов:**
   - Задержка: $< 1.0$ мс (номинально $0.1 - 0.3$ мс).
   - Аллокации: $\le 1$ вектор под буфер форматирования строки.

### 2.2. Пайплайн нечеткого поиска (Search & Match Pipeline)

Выполняется при каждом изменении строки запроса в TUI.

1. **Входные данные:** текущая строка запроса `query: &str`, текущий скоуп (Global vs Local), срез индексов скоупа.
2. **Стадия 0: Тривиальный случай:**
   - Если строка запроса пуста: выборка первых `K = 1000` элементов в порядке убывания времени (reverse chronological). Полнотекстовый движок не запускается.
3. **Стадия 1: Детерминированные фильтры быстрого отсечения (Fast-Reject):**
   - Префиксный запрос `^foo`: проверка первых байт через дескриптор префикса `ByteView.prefix`.
   - Точный подстрочный запрос `'foo`: проверка наличия подстроки без учета регистра.
   - Суффиксный запрос `foo$`: проверка конца строки.
4. **Стадия 2: Векторное битовое отсечение (Bitmask Pruning):**
   - Вычисление 64-битной маски запроса $M_q$.
   - Проход по плоскому массиву `masks: &[u64]`. Если запись не содержит всех символов запроса, она отсеивается.
5. **Стадия 3: Nucleo / SIMD Fuzzy Matcher:**
   - Использование изолированных локальных контекстов потоков (Thread-Local Scratchpads): буфер преобразования UTF-32 и внутренние таблицы состояний матчера переиспользуются, исключая аллокации в куче на строку.
   - **Ограниченная минимальная куча (Bounded Min-Heap Top-K):**
     - Поддерживается куча емкостью ровно $K = 1000$ кандидатов (`score: u32, idx: u32`, 8 байт).
     - Элемент с минимальным скором всегда находится на вершине (`heap.peek()`).
     - Если скор кандидата меньше минимального в куче при ее заполнении, кандидат отбрасывается за $O(1)$.
     - Сложность: $O(N \log K)$ вместо $O(N \log N)$.
6. **Параллелизм:**
   - Если количество записей $< 500$: строго последовательный проход в текущем потоке (оверхед распределения Rayon превышает выигрыш от параллелизма).
   - Если $\ge 500$: параллельное разбиение на чанки (размер чанка $32\,768$ элементов) через пул потоков, локальные кучи в потоках, финальный $K$-way merge.
7. **Бюджет ресурсов:**
   - Задержка: $< 5$ мс на 100 000 записей (номинально $1.5 - 2.5$ мс).
   - Аллокации: 0 байт в горячем цикле сопоставления.

### 2.3. Пайплайн отрисовки кадра (Frame Render Pipeline)

Отрабатывает при получении событий ввода, ресайза окна или таймера (50 мс tick rate).

1. **Компоновка экрана (Layout Calculation):**
   - Вычисление геометрии областей: History (список), Query (строка ввода), Preview (детальный просмотр), Footer (подсказки клавиш).
   - Адаптивная высота панели предварительного просмотра: динамический подсчет строк с учетом переходов строк и ширины терминала.
2. **Синхронизация окна просмотра (Viewport Lookahead Windowing):**
   - Вычисление смещения `viewport_offset` с учетом буферной зоны `scroll_offset` (scrolloff). Курсор не приближается к физической границе фрейма ближе, чем на `scroll_offset` строк.
3. **Отрисовка видимых строк (History Row Rendering):**
   - Отрисовываются _только_ строки, попадающие в видимый диапазон терминала ($\le 50$ строк).
   - **L1 Direct-Mapped Token Cache (2048 слотов):** для невыделенных строк AST-токены и готовые span-структуры извлекаются из кэша по FNV-1a хешу строки. Повторный парсинг не выполняется.
   - Наложение оверлея подсветки совпавших символов запроса поверх синтаксических цветов.
4. **Отрисовка предварительного просмотра (Syntax Preview):**
   - Команда выбранной записи парсится через Tree-sitter Bash Parser в concrete syntax tree.
   - Кэш предпросмотра (128 слотов) исключает повторный запуск парсера при удержании курсора на элементе.
5. **Дифференциальный сброс в терминал:**
   - Отрисовка буфера различий (double-buffering) через ANSI Escape-команды в `stderr`.
6. **Бюджет ресурсов:**
   - Задержка: $< 3.0$ мс на кадр (комфортно для 120 FPS).
   - Аллокации: строго ограничены строковыми срезами отображаемых строк.

## 4. Граничные случаи и системные контракты (Edge Cases & System Contracts)

### 4.1. Контракт восстановления терминала (Fail-Safe Terminal Restoration)

Интерактивный TUI переводит терминал в raw-mode и переключается на альтернативный экран (`AlternateScreen`). Нарушение восстановления при падении оставляет пользовательскую оболочку в неработоспособном состоянии (отсутствие эха, залипание курсора).

- **Panic Hook Invariant:** До входа в raw-mode регистрируется глобальный обработчик паники `std::panic::set_hook`. При возникновении любой паники внутри Rust-рантайма хук обязан выполнить:
  1. `crossterm::terminal::disable_raw_mode()`
  2. Вывод последовательностей выхода: `\x1b[?1049l` (LeaveAlternateScreen), отключение захвата мыши, включение отображения курсора (`\x1b[?25h`).
  3. Сброс стиля курсора в стандартный пользовательский.
  4. Передачу управления оригинальному panic hook для печати backtrace в стандартный поток ошибок.
- **Unix Signal Recovery:** Перехват сигналов `SIGINT` и `SIGTERM`: обработчик выполняет экстренный сброс терминала в дефолтное состояние, сбрасывает диспозицию сигнала на `SIG_DFL` и повторно инициирует сигнал через `raise()`, гарантируя корректный код завершения процесса в родительской оболочке. Сигнал `SIGWINCH` игнорируется на уровне ядра (`SIG_IGN`), так как событие изменения размера окна перехватывается подсистемой событий терминала.

---

### 4.2. Контракт обнаружения возможностей терминала и 4-уровневый Fallback темы

Определение цветовой схемы (Dark/Light) выполняется по строгому каскаду с жесткими тайм-аутами:

```
[Tier 1: Hardware Probe]
OSC 11 Background Query + DA1 Sentinel (\x1b]11;?\x1b\\\x1b[c)
   │
   ├── Поддерживается -> Парсинг RGB -> BT.709 Luma -> Dark / Light (Задержка: < 2ms)
   │
   └── Не поддерживается -> Сторож DA1 возвращает \x1b[?...c -> Abort Probe (< 2ms)
         │
         ▼ Fallback
[Tier 2: Environment Variables]
$COLORFGBG -> индекс цвета фона (0..6, 8 -> Dark; 7, 9..15 -> Light)
$ITERM_PROFILE -> наличие подстроки "light"/"white" или "dark"/"black"
         │
         ▼ Fallback
[Tier 3: OS / Desktop Environment Preferences]
macOS: `defaults read -g AppleInterfaceStyle` ("Dark" -> Dark, иначе Light)
Linux: D-Bus org.freedesktop.portal.Settings color-scheme (1 -> Dark, 2 -> Light)
         │
         ▼ Fallback
[Tier 4: Hardcoded Default]
Темная палитра (Pure Dark Theme)
```

- **Решение проблемы зависания на терминалах без поддержки OSC 11:**
  Если терминал не поддерживает запрос цвета фона OSC 11, он молча проигнорирует последовательность, что при наивной реализации вызвало бы блокировку до истечения полного тайм-аута (50 мс). Добавление сторожевого запроса DA1 (`\x1b[c`) гарантирует, что _любой_ ANSI-совместимый терминал немедленно вернет идентификатор устройства, оканчивающийся на символ `'c'`. Если ответ DA1 получен, а ответ OSC 11 отсутствует — зондирование немедленно прекращается без ожидания тайм-аута.

---

### 4.3. Конкурентный доступ и целостность файловой структуры

- **Отсутствие межпроцессных блокировок (No File Locks):**
  Система принципиально не использует `flock` / `fcntl` при записи в историю.
  - _Обоснование:_ блокировки файлов на сетевых файловых системах (NFS, SMB) либо в высоконагруженных средах с множеством параллельных окон терминала приводят к взаимным блокировкам (deadlocks) и зависанию шелла.
  - _Гарантия:_ Использование флага `O_APPEND` на уровне ядра POSIX гарантирует, что каждый системный вызов `write()` атомарно помещает данные в текущий физический конец файла. Поскольку длина сериализованной строки команды практически никогда не превышает размер буфера страницы (4 КБ), разрыв строк между параллельными процессами исключен.
- **Устойчивость к повреждению записей (Tolerant Parser):**
  - При чтении через `mmap` файл сканируется побайтово в поисках разделителей `\n`.
  - Если последняя строка файла не содержит завершающего `\n` (процесс записи был аварийно прерван по `SIGKILL` или отключению питания), строка парсится до конца доступного среза памяти.
  - Любая строка, содержащая количество полей $\neq 5$, пропускается без остановки обработки валидных строк.

### 4.4. Инварианты буфера поиска и навигации

- **UTF-8 Cursor Invariant:** Позиция курсора в строке запроса измеряется исключительно в количестве логических символов (Unicode Scalar Values), а не в байтах. Удаление и вставка символов используют строго `char_indices()`. Смещение курсора никогда не указывает внутрь многобайтовой UTF-8 последовательности.
- **Scrolloff / Lookahead Cushion:** Вьюпорт отображения истории всегда удерживает буферную зону из $M = \min(\text{scroll\_offset}, (\text{visible\_rows} - 1) / 2)$ строк до верхней и нижней границы видимого фрейма. Это предотвращает визуальное "прилипание" курсора к границам экрана при быстром пролистывании.
- **Обработка изменения размеров терминала:** При сжатии окна терминала до размеров, меньших минимального фрейма ($W < 20$ или $H < 5$), система корректно схлопывает панели Preview и History, предотвращая панику отрисовщика от отрицательных или нулевых ограничений геометрии (`Constraint`).

## 6. Сводная матрица архитектурных инвариантов системы

1. **Инвариант чистого фильтра Unix:** `stdout` содержит _только_ результат работы (команду). TUI, ошибки и диагностика направляются _только_ в `stderr`.
2. **Инвариант zero-lock записи:** Все процессы записи используют исключительно системный режим ядра `O_APPEND`. Межпроцессные мьютексы и файловые блокировки запрещены.
3. **Инвариант zero-copy чтения:** Ни одна строка команды из персистентного файла не копируется в кучу при чтении и поиске. Все строковые срезы оперируют либо внутренними регистрами `ByteView` (до 12 байт), либо прямыми ссылками на виртуальную память `mmap`.
4. **Инвариант предсказуемой задержки:** Время отклика поискового конвейера на нажатие клавиши строго детерминировано и не превышает 5 мс для баз объемом до $10^6$ строк благодаря двухэтапному отсечению (64-битные битовые маски символов + ограниченная Top-K куча).

Контракт дедупликации при поиске: В п. 2.2 (Min-Heap Top-K) не указано, как схлопываются дубликаты одинаковых команд (оставляется только самая свежая запись до/во время вставки в кучу или нет). Для истории шелла это критичный инвариант.
Полная матрица CLI-аргументов: В тексте вскользь упоминаются record, search и grep_entries. Нужен точный список всех подкоманд и флагов CLI (включая генерацию шелл-хуков init fish/zsh/bash, если она есть), чтобы агент спроектировал ручной парсер аргументов без clap.
Противоречие по Regex в record (п. 2.1 vs раздел 5): В пайплайне record заявлены регулярные выражения (Deny/Mask) с бюджетом < 1.0 мс, но крейта regex нет в таблице зависимостей. Компиляция тяжелого regex при каждом нажатии Enter в шелле убьет бюджет задержки — нужно явно зафиксировать либо простые префиксы/подстроки, либо regex-lite, либо вынос фильтрации.
